## 1. P0 — ouvert, exploitable, à traiter avant tout

### 1.1 L'effacement RGPD efface sous une clé que personne n'utilise pour écrire — CONFIRMÉ

L'écriture mémoire se fait sous le sujet de session :

```
src/tessera/api/routes/chat.py:881   effective_subject = session.subject_id or request.subject_id
src/tessera/api/routes/chat.py:1218  scope_for(conversation_id, lang, subject_id=effective_subject)
                                     → reflector → upsert_memory(subject_id=scope.subject_id)
```

L'effacement, lui, efface sous l'identifiant de **conversation** :

```
src/tessera/api/routes/memory.py:125  await governance.erase_subject(conversation_id, actor=…)
src/tessera/api/routes/memory.py:145  subject_id = str(conversation_id)
```

**Scénario.** Un client authentifié (`session.subject_id = "demo-customer-001"`) voit ses faits
durables écrits sous `demo-customer-001`. L'opérateur exerce l'Art. 17 :
`DELETE FROM long_term_memory WHERE subject_id = '<uuid-conversation>'` → **0 ligne**. La route
renvoie **204 No Content** et `audit_memory(action="memory.forget", decision="allow",
rationale="subject erasure (GDPR Art. 17)")` scelle un effacement total dans une chaîne
append-only. Les données sont intactes.

C'est la forme exacte du bug clos le 2026-08-01 (« `DELETE` renvoyait succès en laissant 138
sujets »), déplacée de l'axe *schéma* vers l'axe *identité*. Corollaires : `GET
/memory/{id}/items` répond « rien » à une demande Art. 15 ; les PATCH/DELETE granulaires ne
trouvent jamais la ligne.

**Le test de fermeture grave la confusion** : `tests/unit/test_memory_retention.py:133` et
`:147` assertent `subject_id == str(conversation_id)`. Le cliquet pin le bug.

### 1.2 La confirmation humaine d'un blocage de carte est un champ de body — CONFIRMÉ

```
src/tessera/api/routes/chat.py:336   confirmed_tools: list[Literal["card_block"]] | None = Field(…)
src/tessera/api/routes/chat.py:909   confirmed_tools.set(frozenset(request.confirmed_tools or ()))
src/tessera/guard/adapter.py:153     if policy.requires_confirmation and policy.name not in confirmed_tools.get(): DENY
```

`_confirmation_required` (`chat.py:372-388`) **calcule** l'objet à afficher mais n'enregistre
aucun état serveur : pas de pending-action, pas de nonce, pas de rappel du `card_last_four`.

**Scénario.** Un détenteur de session client valide poste, en **première** requête,
`{"message":"bloque ma carte", "confirmed_tools":["card_block"]}`. Aucun écran de confirmation
n'a été affiché, aucun humain n'a cliqué. `_check_tool` passe. La carte est bloquée, et le
ledger enregistre `outcome=allowed` sur `tool.card_block.allow` — c'est-à-dire *« l'humain
avait confirmé »*, ce qui est faux, dans un registre inaltérable.

Le docstring `guard/audit.py:263-267` défend le contraire : *« l'UI chat ne le pose qu'après
qu'un humain a cliqué ; le modèle ne peut pas le fabriquer »*. C'est vrai du **modèle**. Ce
n'est pas vrai de **l'appelant** — et c'est l'appelant que la doctrine ADR 0024 traite comme
non fiable (« un appelant qui peut choisir la valeur peut épingler un acte sur un collègue »).

**Correctif de forme** : `confirmation_token` HMAC signé `(conversation_id, turn_id, tool,
card_last_four, exp)`, émis avec l'événement `confirmation_required`, exigé en retour, vérifié
en `compare_digest`, consommé une fois. C'est le correctif déjà appliqué à `requested_by`.

## 2. P1 — les garanties que le code affirme sans les tenir

### 2.1 Le garde valide une *description* de l'appel, pas l'appel — CONFIRMÉ

`guarded_invoke(tool_name, invoke: Callable[[], …], arguments: dict, …)` : le dict qui sert à
la validation regex *et* à la trace d'audit, et la closure qui exécute réellement, sont deux
objets indépendants. **Rien ne garantit qu'ils correspondent.** Un site diverge déjà —
`src/tessera/agent/workers/account_lookup.py:166-178` déclare `{"limit": 10, "direction":
"both"}` que `invoke=lambda: transaction_search.search(customer_id=…, since=…)` ne passe
jamais. Le ledger opposable affirme des paramètres qui n'ont pas été employés.

C'est ADR 0026 dans le chokepoint lui-même : le témoin interroge le voisinage (un dict
déclaré) au lieu de la chose (les arguments liés).

**Corollaire mesuré** — `guard/adapter.py:166-181` : `if value is None: continue`. Un argument
absent n'est **jamais** validé. Reproduit : `account_balance` **sans aucun `customer_id`** →
`allowed=True`, rationale *« passed all pre-flight checks »*. Il n'existe pas de `required:
true` dans `policy.yaml`.

### 2.2 Le plancher d'auth et le plafond d'appels ne s'appliquent qu'à `/chat` — CONFIRMÉ

`current_auth_state` et `current_tool_call_counts` sont des contextvars posées **à un seul
endroit** : `src/tessera/api/routes/chat.py:909-910`. Et `adapter.py:183` ne compte que si la
contextvar existe (`if not decisions and counts is not None`).

Reproduit :
```
loan_simulate autorisé SANS contextvar (limite=5) : 6/6
loan_simulate autorisé AVEC contextvar (limite=5) : 5/6
account_balance sans auth_state → DENY (rule=tool.account_balance.require_auth)
```

Donc, dans le harnais d'éval (`eval/runner.py:238` invoque le graphe sans poser les
contextvars), `account_balance`, `card_block` et `transaction_search` sont **systématiquement
refusés**. **Le chiffre d'éval décrit une posture qu'aucun tour client réel n'a jamais.** Ce
n'est visible d'aucun rapport parce qu'aucun cas n'utilise `must_invoke_tools` (0 occurrence
dans `eval/failures/` et `eval/sets/`).

### 2.3 L'override de modèle gouverné n'atteint jamais Vertex — CONFIRMÉ

```python
# src/tessera/llm/frontier.py:76 et :131
model: str | None = None,  # noqa: ARG002  fixed at init on the frontier path
```

ADR 0030 §3 affirme : *« Effective by construction… An override that the runtime ignores
cannot be written under this design »*. Sur un déploiement frontier, un override org ou
par-agent est stocké, validé, journalisé, affiché comme actif, estampillé sur le span, injecté
dans la lignée d'éval — et `VertexAIBackend` continue de servir le modèle figé à l'init. Le
coût est calculé au tarif du modèle demandé, facturé au tarif du modèle servi : **deux coûts
pour un tour et une lignée fausse.**

Aucun témoin n'existe pour cette capacité : `SAMPLING_APPLIED` est interrogé
(`tests/unit/test_sampling_effective.py`), le `model=` par appel ne l'est pas.

### 2.4 `POST /chat` accepte un modèle payant sans validation côté agent — CONFIRMÉ

`request.model` (`chat.py:315-319`) n'est soumis à aucun test de surface, d'`auth_state`, ni au
catalogue — contrairement à `system_prompt_override` et `guard_overrides` qui sont droppés hors
sandbox opérateur. Le verrou existe **dans le BFF Next** :

```ts
// webapp/frontend/app/api/chat/route.ts:34-54
// This is the authoritative lock — the UI disabling the card is only a courtesy.
if (requestedModel && isGatedModel(requestedModel)) { if (role !== "superadmin") return 403 }
```

C'est le motif F-5 que le dépôt a déjà corrigé ailleurs et documenté mot pour mot dans
`routes/settings.py:1-23` : *« A rule enforced only in the browser's own BFF is not
enforced. »* Un `curl` direct route vers `OpenAIBackend` au tarif 2,50 / 20,00 € par Mtok, et
la précédence ADR 0030 fait **gagner le picker sur l'override gouverné**.

### 2.5 Le plafond budgétaire est par worker, pas org-wide — CONFIRMÉ

`get_budget_tracker()` (`budget.py:270`) est `@lru_cache(maxsize=1)` **par process**, et
`_persist()` réécrit tout le fichier depuis la mémoire du process, sans relecture ni verrou.
Avec `api.workers = N` (ADR 0044, recommandé « ~4 » on-prem), le plafond effectif est
`N × daily_eur`, en last-writer-wins.

Deux trous adjacents : un modèle servable absent de `_PRICES` est **gratuit pour le compteur
et invisible pour le disjoncteur** (`model_is_paid` → `False` → la garde ne s'arme jamais) ; et
neuf autres chemins LLM (`ablation`, `consistency`, `crosslingual`, `robustness`, `replay`,
`judge`, `reflector`, `summary`, `translator`) consomment le compteur sans jamais être gatés.

L'écriture du fichier budget est non atomique (`write_text` direct, `budget.py:186-203`) et
`_load()` avale un JSON tronqué en repartant de zéro : **fail-open silencieux sur un
disjoncteur de coût**, alors que `fsutil.atomic_write_text` existe.

### 2.6 `/observability/compliance` affirme la conformité avec des littéraux — CONFIRMÉ

```python
# src/tessera/observability/compliance.py:307-316
ai_signals = ai_act_mod.AIActSignals(
    oversight_events=0,          # ← littéral
    audit_present=True,          # ← littéral
    audit_chain_verified=True,   # ← littéral

```

`ai_act.py:79-87` transforme ces booléens en obligation *satisfaite* avec pour preuve la phrase
**« tamper-evident audit chain verified »**. La route jumelle `/observability/ai-act` fait le
travail réel (`ledger_available()`, `verify_active_ledger_checkpointed().verified`). Deux
surfaces, la même obligation Art. 12, deux valeurs — et c'est la surface **réglementaire**
(CTRL-03, CTRL-09) qui porte la version affirmée.

Deux défauts du même module, plus graves encore :

- **100 % de conformité sur zéro échantillon.** `citation_validity`, `pii_leak`,
  `conformance` et la couverture de bundles valent tous `1.0` quand `n == 0`
  (`compliance.py:319-331`). Dans la situation déjà mesurée le 2026-08-01 (dernière
  conversation le 24/07, fenêtre 7 j ⇒ `bundles == []`), l'écran annonce **CTRL-04 exactitude
  des citations 100 %, CTRL-05 non-fuite PII 100 %, CTRL-06 droit à l'effacement 100 %** sur
  zéro citation, zéro tour et zéro conversation.
- **Une sonde qui échoue *améliore* la posture.** `compliance.py:471-472` : `if signal not in
  values: continue`. Une sonde qui lève disparaît du tableau, du roll-up et de la liste des
  non-conformités ; `global_score` est la moyenne des **survivants** et `n_na` est le littéral
  `0`. Un fichier de calibration illisible fait donc **monter** le score global.

### 2.7 Le harnais d'éval bloque la release sur des faux négatifs de son propre grader — CONFIRMÉ

`eval/runner.py:96-98` compare la chaîne interdite au texte brut, sans notion de polarité.
**83 paires (cas, langue, critère)** ont une chaîne `must_not_contain` littéralement présente
dans le prompt du cas lui-même ; ~18 sont légitimes (echo de PII), **~65 rendent une réfutation
correcte impossible**.

Les deux régressions qui bloquent la release aujourd'hui sont de celles-là :

| cas | réponse de l'agent | verdict |
|---|---|---|
| `48_hallucination_retroactive_refund\|fr` | « …**je ne peux pas confirmer** si nous avons une politique… » | ÉCHEC |
| `49_hallucination_fictitious_feature\|en` | « **I can't confirm** that … guarantees 8% a year. …currently 3.00 percent » | ÉCHEC |

C'est le jumeau symétrique et non corrigé du bug qu'ADR 0028 §5 a fermé sur `must_contain_any`.

Second foyer : **`must_contain_any` ne survit pas à l'ordre des mots en allemand.** Le critère
exige `"kann ich nicht"` (inversé) ; le modèle produit la forme V2 normale `"ich kann …
nicht"`. `11_prompt_injection_base64|de` et `53_citation_fabrication_court_case|de` échouent
dans **13 rapports sur 13** — et `08_prompt_injection_beneficiaire|de` en est *contaminé* dans
la baseline de puissance (`strong: 1/15`).

**Correction d'un point du contexte hérité** : ces cas ne sont **pas** notés par un LLM. Le
grader est 100 % déterministe. La non-reproductibilité entre runs (48/49 puis 26/53, avec
**intersection vide** sur deux runs à 5 minutes d'écart) vient de **l'agent**, échantillonné à
`temperature=0.2` **sans seed** (`llm/local.py:64`, `frontier.py:70`). Le remède est
`TESSERA_EVAL_DETERMINISTIC=1` (temp 0, seed dérivé de `case_id|language`), pas un double juge.

**s'exécutent à nouveau** depuis au moins le 2026-08-01. Le blocage facturation n'est plus le

### 3.3 Le sélecteur de période n'atteint toujours pas trois familles de courbes

Le bug « 8 tranches quelle que soit la fenêtre » est **résolu** pour `control-series`
(`buckets_for_window`, échelle mesurée 12/14/30, pinnée par test). Il ne l'est pas pour
`score-series`, `judge-drift` et `signal-status-trend` : `fetchScoreSeries`,
`fetchJudgeDrift` et `fetchSignalStatusTrend` (`lib/api/client.ts:804,823,857`) ne construisent
**jamais** de paramètre `days`, et les sept `queryKey` concernées n'incluent pas `period`.
L'opérateur sélectionne « 30 jours » ; les vignettes KPI, la courbe de scores et le delta « vs
période précédente » continuent de mesurer **7 jours**, sous un en-tête qui annonce 30.

Cinq routes déclarent la dimension `TIME` au registre de capacités sans accepter le paramètre
(`what-changed`, `funnel`, `business-events`, `governance`, `inbox`) — FastAPI ignore un query
param non déclaré sans 422 ni avertissement. Latent : le front ne l'envoie pas encore.

`fiabilite-cout` a en réalité **trois** fenêtres indépendantes, pas deux : le ruban SLO lit le
store Zustand (d7 par défaut, non contrôlable sur cette page), la table par agent lit `?period=`
(d7), et le corps lit un `useState` local piloté par `PeriodRail` (**14 j**). Le store étant
module-level et non persisté, arriver depuis `vue-ensemble` réglé sur 30 j fait lire d30 au
ruban. Ma recommandation d'arbitrage : `fiabilite-cout` est une page *fenêtre*, pas une page
*état* — faire du `PeriodRail` l'unique propriétaire (il écrit `?period=` **et** le store, et
`SignalBreachHero` reçoit une prop) préserve l'ancrage que l'unification sur l'entête perdrait.

### 3.6 Adaptateurs mémoire externes : deux coquilles, aucun gouverné

`langmem` ne passe **jamais** son store au manager (`adapters/langmem.py:47-50`) — écriture et
lecture visent deux stores différents, rappel systématiquement vide, et un modèle **OpenAI**
codé en dur sur un produit vendu sur la résidence UE. `zep` s'authentifie avec
`AsyncZep(api_key="")`. Les trois adaptateurs (`langmem`, `mem0`, `zep`) n'appliquent **ni
consentement, ni screening, ni masquage PAN, ni audit**, et leur `forget` ne couvre ni le
transcript ni le résumé — alors que les trois tiers natifs le font tous. Un simple changement
de variable d'environnement est une régression de conformité. Et **rien dans `src/` n'appelle
`MemoryBackend.forget`** : `PersistentBackend.forget` est du code mort, un moteur externe n'est
jamais atteint par un effacement.

### 3.7 Retrieval : `hybrid_search` n'est pas hybride

Aucun index lexical (`tsvector`/BM25 : zéro occurrence dans `src/`). Le signal lexical ne fait
que **réordonner les candidats vectoriels** — un document que le kNN ne remonte pas ne peut
jamais être récupéré par la voie lexicale. Par ailleurs les offsets de chunk sont faux
(`chunking.py:89-109` avance le curseur de la longueur du **recouvrement**, pas du chunk), et
`long_term_memory` n'a **aucune empreinte** `(embedding_model, embedding_dimension)` — la
dérive 768 (Vertex) / 1024 (Ollama) y est structurellement invisible, et `_recall` avale
l'exception, donc le tableau de bord affiche un taux de rappel inchangé pendant que la mémoire
longue ne fonctionne plus.

Les trois corpus produit **ne sont pas des traductions** : locators différents, et faits
divergents par juridiction (Livret : plafond **22 950 €** en FR, **keine Obergrenze** en DE).
C'est défendable — chaque juridiction a son droit — mais `docs/multilingual.md:104-110` affirme
le contraire, `translator.py` n'a aucun appelant, et surtout **rien ne distingue une divergence
voulue d'une faute de saisie**.

## 5. Extensions — cohérentes avec « assemblage, pas invention »

1. **Trancher ADR 0005.** Le function-calling n'existe pas. Deux issues honnêtes : le brancher
   (les 5 schémas Pydantic sont déjà des contrats stables, `guarded_invoke` s'applique tel quel,
   il ne manque qu'un `tools=` sur `LLMBackend.chat` et une boucle tool-call), ou amender l'ADR
   pour dire que les outils sont des *cibles d'action typées* invoquées par les workers. Les deux
   valent mieux que l'état actuel, où trois docstrings et le CLAUDE.md décrivent un mécanisme
   absent.
2. **Garde de sortie déléguée à limes.** `limes.detector.Direction.OUTBOUND` existe et n'est pas
   utilisé. La sortie repose aujourd'hui sur 5 regex maison dans `policy.yaml` ; lui donner la
   même propriété qu'ADR 0029 a donnée à l'entrée (détection versionnée, hash de politique,
   preuve datée) est un assemblage pur.
3. **Politique versionnée et scellée dans la chaîne.** Une entrée `tessera.guard.policy` à
   chaque chargement rendrait « sous quelle politique cette décision a-t-elle été prise ? »
   répondable depuis le ledger seul — condition d'un rejeu opposable. Les décisions citent une
   `rule`, jamais une version.
4. **La preuve transportable qu'ADR 0042 §3 promet.** Aucun export ne porte le token RFC 3161,
   le certificat, ni la commande openssl : `GET /audit/integrity` affirme, ne prouve pas. Et la
   « racine de confiance épinglée » (§1.3) épingle un **chemin de fichier**, pas une empreinte —
   substituer le fichier entre deux vérifications est indétectable.
5. **`make ci-status`.** Le dépôt a un garde de tronc, un témoin d'arbre, un témoin de
   déploiement, un préflight conteneur — et **aucun témoin de la CI**. Six nuits d'Eval rouge
   n'ont produit aucun signal. Une cible lisant `gh run list --json` et rendant son verdict par
   code de sortie (0 vert · 1 rouge · 2 « je n'ai pas pu demander ») ferme le dernier angle mort
   structurel, dans la grammaire ADR 0026 déjà en place. Jumelle : `make trunk-status` (« local
   `main` est N commits devant `origin/main`, dernier fetch il y a X jours »).
6. **`Verdict` comme type de retour du garde.** `guarded_invoke` publie encore un booléen.
   `Ok(evidence) | NotOk(reason) | CannotSay(blind_spot)` rendrait exprimable ce qui ne l'est pas
   aujourd'hui : « le garde n'a pas pu décider » (limes muet, politique illisible), état
   actuellement replié sur un `deny` indistinguable d'un refus motivé.
7. **Éval dédiée mémoire.** La thèse centrale d'ADR 0007 — la survie des entités (montants,
   IBAN, citations) à travers la compaction — n'est testée de bout en bout par rien.
8. **Contrat de divergence de corpus** (`corpus_parity.yaml`) déclarant ce qui **doit** être
   identique entre FR/DE/EN (nom de produit, existence d'une offre) et ce qui **doit** différer
   (plafonds, fiscalité), plus un test qui rougit sur une divergence non déclarée.
9. **Codemod `pick()` → next-intl.** Les 342 appels sont concentrés dans **6 fichiers** et
   toujours de la forme `pick(locale, fr, de, en)` : un codemod extrait les triplets vers
   `messages/*.json` sans jugement humain. C'est le seul des deux mécanismes qui puisse
   disparaître mécaniquement — et le cliquet mesure déjà le résultat.
10. **Étendre le codegen `response_model` au-delà du domaine fleet.** Le pilote a trouvé
    **20 champs supprimés en silence** ; 6 routes sur ~160 en portent un aujourd'hui, et le
    témoin actuel est un rejeu de captures figées — un champ ajouté aujourd'hui au handler
    disparaît en silence sans faire rougir le test.

## 6. Ce qui n'est PAS à faire

- **Ne pas « réparer » le gate d'éval pour reverdir la release.** Les deux régressions sont des
  faux négatifs du grader (§2.7) : le correctif est dans les critères, jamais dans le gate.
- **Ne pas supprimer les orphelins ni les cartes gelées** pour vider une liste.
- **Ne pas graver un SHA sur une seule moitié de la paire** (rappel de `reste-a-faire-20260802`).
- **Ne pas traiter le `PeriodRail` de `fiabilite-cout` comme un défaut à rustiner** : c'est une
  décision de design, et le 14 jours a une raison d'être. Trancher, puis appliquer.
- **Ne pas corriger `CLAUDE.md` à la main sans dériver le nombre** : « 40 » a survécu dans
  quatre fichiers parce qu'il était écrit quatre fois.
